## Phase 1

- **Discovered and fixed a class of pre-existing broken JavaScript unrelated to the original brief.** While fixing an em dash, an edit exposed that the surrounding string had an unescaped apostrophe that would break JS parsing. That prompted a full scan of every inline `<script>` block in every HTML file. Fixed all of them and re-verified with `node --check` across every script block in the repo. Documented in full in AUDIT.md section 13a. This is outside the letter of "Phase 1: cleanup, link repair, language sweep, QA backlog" but squarely inside its spirit (remove dead code flagged in audit / fix confirmed issues) and the ground rule to retry any edit until grep-verified: so it was fixed rather than just logged.

After manual verification only 27 real prose hits remained and were fixed. **Why this matters for later phases:** don't trust raw word-list regex counts for copy audits in this codebase without checking surrounding context first: the false-positive rate from CSS/JS identifiers is very high in these style-heavy monolith files.

Both were carried forward from the previous AUDIT.md without re-verification and turned out to be stale; corrected in AUDIT.md directly rather than silently ignored.
- **"[DEMO] prefix on demo content" was not applied as a sweeping content change.** The demo-mode gate (`crew_auth` localStorage, `gate.html`) is the actual mechanism separating sales-demo access from the rest of the app, and the `.demo-label` divs found in each app are `display:none` dev metadata, not visible content needing a prefix. The sample data throughout the app (contractor names, bookings) is inherent placeholder content for what is, at this stage, a UI prototype backed by Phase 5-6 real data wiring: adding "[DEMO]" text prefixes to every sample name across 8MB+ of markup would be a large, low-value, cosmetic change with no clear single insertion point. - **ARIA on tab navigation**: applied `role="tablist"`/`aria-label` to the repeated bottom-nav container and `role="tab"`/`aria-selected` to its buttons across the three main apps (113-116 buttons per file). Did not touch the one `.nav-item` class found only in Crew_App_Crew_Manager.html, which appears to be a different, unrelated component.

## Phase 2

- **Critical finding: `payments/routes.js` never imported `createClient` from `@supabase/supabase-js`, despite calling it 11 times.** This meant charge, job-complete, approve-release, dispute, refund, cancel, ledger, status, methods and both onboarding endpoints would throw a runtime `ReferenceError` the instant any of them was actually invoked. `node --check` cannot catch this class of bug (it's a reference error, not a syntax error): only actually `require()`-ing the module and confirming it loads catches it. Fixed with a one-line import; re-verified by requiring the module. This is now a standing lesson for the rest of this run: syntax-checking alone is not enough evidence a module works, and a quick `require()` smoke test is cheap insurance.
- **The dispute endpoint (`POST /api/payments/dispute`) only allowed the customer to raise a dispute**, even though the brief says either party may. Widened to party-scoped (customer OR contractor), matching how `job-complete` and `approve-release` already reference the correct party.
- **Two onboarding endpoints trusted a client-supplied `zaiUserId`** (`POST /onboarding/bank-account` took it straight from the request body; `GET /onboarding/status/:zaiUserId` took it from the URL with no ownership check): meaning any authenticated user could attach a bank account to, or read the KYC status of, any other user's provider account just by knowing or guessing their id. Fixed: bank-account now derives the caller's own `zai_user_id` from their profile row server-side (ignoring anything client-supplied); status now checks the caller owns that id or is an admin.
- **`lib/notify.js` was completely rewritten.** The version on disk (`notifyAdmin`, admin-only, email via Resend, writes to `admin_notifications`) is kept as a distinct export for genuine ops alerts, but it was not what any payment/booking event should call and nothing in the codebase called it yet, so nothing broke. The real `notify(userId, {title, body, link, type})` contract the brief specifies is now the primary export: writes to `notifications` (read by the in-app bell) and sends Web Push to every device on file for that user via the newly-added `sendPushToUser` helper, pruning subscriptions on 404/410.
- **`push_subscriptions` usage was rebuilt from one-row-per-user (overwritten on every new device) to one-row-per-endpoint**, so a user subscribed on both their phone and laptop keeps both working. This required rewriting `POST /api/push/subscribe` to upsert on `endpoint` instead of `user_id`, and adding `POST /api/push/unsubscribe`. The Phase 5 migration will formalise this exact shape (`id, user_id, endpoint unique, p256dh, auth, user_agent, created_at`); the code was written against that shape now even though the table doesn't exist until Phase 5 runs, consistent with how the rest of this codebase already runs ahead of its own schema.
- **`api/push/dispatch.js` created now** (as a plain Node module, not yet wired into Vercel routing: that's Phase 8) alongside the equivalent Express route in `lib/push-routes.js`, so the feature is real and testable locally today via `node server.js`, and Phase 8 only has to wire the URL, not invent the logic.
- **The Web Push settings toggle was wired into the existing (previously decorative, non-functional) "Push Notifications" switch** already present in all three main apps' notification-settings screens, rather than building a new UI element from scratch: reuses the existing `.toggle-switch` visual language and requires no new screen.
- **`/api/config` was added now, ahead of Phase 8's formal serverless-function version**, exposing `vapidPublicKey`/`authAppleEnabled`/`paymentsCardEnabled`/`betaMode` as a plain Express route in server.js. Phase 8 will convert this to a Vercel function; the response shape is written to match what Phase 3/4 client code will expect so it doesn't need to change later.
