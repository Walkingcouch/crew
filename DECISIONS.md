## Phase 2

- **Critical finding: `payments/routes.js` never imported `createClient` from `@supabase/supabase-js`, despite calling it 11 times.** This meant charge, job-complete, approve-release, dispute, refund, cancel, ledger, status, methods and both onboarding endpoints would throw a runtime `ReferenceError` the instant any of them was actually invoked. `node --check` cannot catch this class of bug (it's a reference error, not a syntax error): only actually `require()`-ing the module and confirming it loads catches it. Fixed with a one-line import; re-verified by requiring the module. This is now a standing lesson for the rest of this run: syntax-checking alone is not enough evidence a module works, and a quick `require()` smoke test is cheap insurance.
- **The dispute endpoint (`POST /api/payments/dispute`) only allowed the customer to raise a dispute**, even though the brief says either party may. Widened to party-scoped (customer OR contractor), matching how `job-complete` and `approve-release` already reference the correct party.
- **Two onboarding endpoints trusted a client-supplied `zaiUserId`** (`POST /onboarding/bank-account` took it straight from the request body; `GET /onboarding/status/:zaiUserId` took it from the URL with no ownership check): meaning any authenticated user could attach a bank account to, or read the KYC status of, any other user's provider account just by knowing or guessing their id. Fixed: bank-account now derives the caller's own `zai_user_id` from their profile row server-side (ignoring anything client-supplied); status now checks the caller owns that id or is an admin.
- **`lib/notify.js` was completely rewritten.** The version on disk (`notifyAdmin`, admin-only, email via Resend, writes to `admin_notifications`) is kept as a distinct export for genuine ops alerts, but it was not what any payment/booking event should call and nothing in the codebase called it yet, so nothing broke. The real `notify(userId, {title, body, link, type})` contract the brief specifies is now the primary export: writes to `notifications` (read by the in-app bell) and sends Web Push to every device on file for that user via the newly-added `sendPushToUser` helper, pruning subscriptions on 404/410.
- **`push_subscriptions` usage was rebuilt from one-row-per-user (overwritten on every new device) to one-row-per-endpoint**, so a user subscribed on both their phone and laptop keeps both working. This required rewriting `POST /api/push/subscribe` to upsert on `endpoint` instead of `user_id`, and adding `POST /api/push/unsubscribe`. The Phase 5 migration will formalise this exact shape (`id, user_id, endpoint unique, p256dh, auth, user_agent, created_at`); the code was written against that shape now even though the table doesn't exist until Phase 5 runs, consistent with how the rest of this codebase already runs ahead of its own schema.
- **`api/push/dispatch.js` created now** (as a plain Node module, not yet wired into Vercel routing: that's Phase 8) alongside the equivalent Express route in `lib/push-routes.js`, so the feature is real and testable locally today via `node server.js`, and Phase 8 only has to wire the URL, not invent the logic.
- **The Web Push settings toggle was wired into the existing (previously decorative, non-functional) "Push Notifications" switch** already present in all three main apps' notification-settings screens, rather than building a new UI element from scratch: reuses the existing `.toggle-switch` visual language and requires no new screen.
- **`/api/config` was added now, ahead of Phase 8's formal serverless-function version**, exposing `vapidPublicKey`/`authAppleEnabled`/`paymentsCardEnabled`/`betaMode` as a plain Express route in server.js. Phase 8 will convert this to a Vercel function; the response shape is written to match what Phase 3/4 client code will expect so it doesn't need to change later.

Classified each by its surrounding context (letter-bounded = apostrophe, digit-bounded = numeric range, near "points"/"faster" = multiplication, etc.) and fixed all 303, then found and fixed a further 147 lost decorative emoji (rendered as literal "??" or "????" sequences, e.g. the Australian flag badge, stamp-card icons) by stripping them rather than guessing which specific emoji was originally there, since the bytes genuinely can't be recovered and a wrong guess is worse than a clean removal. Verified no genuine single question marks (real sentence-ending questions) were touched, only 2+ consecutive marks, which cannot occur in genuine English prose.

## Phase 5

- **The Supabase CLI is installed in this environment but has no stored auth token** (`supabase projects list` returns Unauthorized). Per the autonomous defaults, this is treated the same as "CLI not linked": the migrations were written and statically verified (balanced parens, balanced `$$` blocks, no em dashes) but not applied. Even if a token had been present, pushing schema changes to a live production Supabase project without the user watching is exactly the kind of hard-to-reverse action that warrants a real confirmation, not a default autonomous "yes". See supabase/APPLY.md for exact steps.
- **Reconciled the new schema against three pre-existing, never-formally-tracked SQL files** (schema.sql, full_schema.sql, phase2_schema.sql) rather than ignoring them: `profiles`, `organisations`, `beta_allowlist`, `community_reports` and `notifications` already existed there with slightly different columns than this brief's spec (e.g. organisations had `slug`/`plan`/`logo_url`, not `abn`/`provider_account_id`). The migration extends these tables in place with `ADD COLUMN IF NOT EXISTS` rather than dropping and recreating them, so it's safe to run whether or not the legacy files were ever actually applied to the live project. Confirmed by direct search that `bookings`, `escrow_events`, `transactions` and `webhook_events` (all used extensively by `payments/*.js` already) were never defined in any of those legacy files at all, meaning the payments code has been running against tables that don't exist yet, until this migration.
- **`is_beta_allowed`'s parameter is named `p_email`, not `check_email`** (the name used in the pre-existing schema.sql). The Phase 3 client code (auth.html, auth/callback.html) was already written calling `db.rpc('is_beta_allowed', { p_email: ... })`, so the migration matches the new client code rather than the old, unused SQL file.
- **Replaced an initially-drafted RLS `WITH CHECK` policy that tried to block clients from changing their own `role`/`provider_account_id`/`kyc_status`/`paused` via a self-referencing correlated subquery**, after recognising that pattern has a real timing/snapshot ambiguity risk in Postgres RLS. Replaced with the standard, unambiguous approach: `REVOKE UPDATE ON profiles FROM authenticated` plus `GRANT UPDATE (specific safe columns) TO authenticated`, which is column-level Postgres privilege, not a policy trick, and is well-established practice.
- **`bookings.ref` was initially drafted using `floor(random()*99999)` for its human-readable reference number**, then corrected to a real `SEQUENCE` before committing, since a random default has a non-zero collision probability under a UNIQUE constraint (would surface as an occasional insert failure and a confusing retry) whereas a sequence is collision-free by construction.
- **`0002_seed_dev.sql` seeds only `beta_allowlist` and a demo `organisations` row**, not any `profiles`/`bookings`/`quotes` demo data, because every one of those tables' user-facing rows must reference a real `auth.users` row, which can only be created by an actual sign-up, not a plain INSERT. Documented the manual promote-to-admin step for after a real dev sign-up instead of faking it.
- **Storage bucket creation and policies are documented in APPLY.md as manual Dashboard/SQL steps, not part of the migration file**, since Supabase Storage buckets are typically provisioned through the Dashboard or Storage API rather than plain SQL, and the exact policy SQL depends on the object-path convention Phase 7's upload code ends up using.
