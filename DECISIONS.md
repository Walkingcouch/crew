## Phase 2

- **Critical finding: `payments/routes.js` never imported `createClient` from `@supabase/supabase-js`, despite calling it 11 times.** This meant charge, job-complete, approve-release, dispute, refund, cancel, ledger, status, methods and both onboarding endpoints would throw a runtime `ReferenceError` the instant any of them was actually invoked. `node --check` cannot catch this class of bug (it's a reference error, not a syntax error): only actually `require()`-ing the module and confirming it loads catches it. Fixed with a one-line import; re-verified by requiring the module. This is now a standing lesson for the rest of this run: syntax-checking alone is not enough evidence a module works, and a quick `require()` smoke test is cheap insurance.
- **The dispute endpoint (`POST /api/payments/dispute`) only allowed the customer to raise a dispute**, even though the brief says either party may. Widened to party-scoped (customer OR contractor), matching how `job-complete` and `approve-release` already reference the correct party.

Fixed: bank-account now derives the caller's own `zai_user_id` from their profile row server-side (ignoring anything client-supplied); status now checks the caller owns that id or is an admin.

- **`push_subscriptions` usage was rebuilt from one-row-per-user (overwritten on every new device) to one-row-per-endpoint**, so a user subscribed on both their phone and laptop keeps both working. This required rewriting `POST /api/push/subscribe` to upsert on `endpoint` instead of `user_id`, and adding `POST /api/push/unsubscribe`. The Phase 5 migration will formalise this exact shape (`id, user_id, endpoint unique, p256dh, auth, user_agent, created_at`); the code was written against that shape now even though the table doesn't exist until Phase 5 runs, consistent with how the rest of this codebase already runs ahead of its own schema.

## Phase 8

- **The whole Express app deploys as one Vercel serverless function** (`api/index.js` re-exports `server.js`, which now only calls `app.listen()` when run directly via `require.main === module`, and always exports the `app`). - **The user's Vercel CLI was already authenticated and the `crew` project already linked to the live `getcrew.com.au` domain** (a prior session's work), so the deploy the user asked for was actually possible, unlike the schema push (Supabase CLI still unauthenticated, see below). - **Found and fixed a real, live production bug during that smoke test**: every clean-URL rewrite whose destination `.html` filename didn't match the source path's own basename (`/login` -> `auth.html`, `/dashboard` -> `CrewBase_Dashboard.html`, `/customer` -> `Crew_App_Customer_Role.html`, `/portal`, `/command`, `/manager`, `/contractor`, `/signin`, 8 routes total) 404'd live, while same-basename rewrites (`/apps` -> `apps.html`, `/reset-password` -> `reset-password.html`) worked fine. Root cause: `cleanUrls: true` redirects direct `.html` requests to their extensionless form, and a rewrite's `"check": true` re-evaluation of a mismatched-basename `.html` destination runs back into that redirect rule internally, which doesn't resolve to servable content the way a matching-basename request does (Vercel appears to special-case the same-path case, not the general one). Confirmed by testing the extensionless form of each destination file directly (200 in every case), then fixed by rewriting all 54 affected `rewrites` destinations in `vercel.json` to their extensionless clean-URL form programmatically, rebuilt, redeployed, and re-curled all 31 clean routes plus the API/asset spot-checks: all 200/401-as-expected. This is exactly the class of bug DEPLOY.md's curl-every-rewrite checklist was written to catch, and it did, just needed an actual live deployment to trigger it since local `node server.js` never exercises Vercel's own routing/cleanUrls behaviour at all.
